## 0. 决策记录（ADR）

以下取舍已经过对照评审定案，后续不再重新争论；推翻任何一条需给出新事实。

| # | 决策 | 结论 | 理由摘要 |
|---|---|---|---|
| 1 | 配置校验用 pydantic？ | **否**，stdlib dataclass + json | 项目钉死 macOS python3.9 + requirements 全锁定，无 pydantic 先例、dataclass 有先例（risk/engine.py） |
| 2 | 配置深冻结（frozen dataclass + MappingProxyType）？ | **否**，dict snapshot + 校验 | 全部测试注入手法依赖 CFG 可变（test_execution 的 `set_gate()` 原地 mutate `runner.CFG`、test_review 消费 `daily.START_CASH`）；深冻结收益撑不起迁移风险 |
| 3 | repo 函数返回 dataclass？ | **否**，返回值保持被替换处现状形状（tuple/标量） | 30+ 调用点解包方式不变，迁移是纯移动；sqlite3.Row 本身同时支持 `row[0]`/`row["name"]` |
| 4 | 前端虚拟化（@tanstack/react-virtual）？ | **否**（暂缓） | 实测数据全部有界：watchlist 82 只、decisions 服务端 clamp 50、news 30、candles 120 根、backtest 3KB JSON；82 行列表虚拟化用户感知为零。数据量级涨到中证800全量上 UI 时再议 |
| 5 | `prev_close` 收进 market.py？ | **否** | 三处语义不同：paper 用 `OFFSET 1` 取次新 bar、review 按指定日期锚（`trade_date<?`）、movers 取实时 K 线第二根；且带 conn 参数破坏 market.py stdlib-only 纯函数定位 |
| 6 | 写接口加 CSRF token？ | **否** | 报告描述的机制是虚构的；项目已有 Host 白名单 + Origin 精确比对防护（09-13 修，server.py:1092-1111），等效有效 |
| 7 | AGSICKLE_* 收编进统一配置层？ | **否** | 4 个运行时开关（DISABLE_LIVE_QUOTES/SLIPPAGE/NOTIFY/ALLOW_UI）是测试逃生门不是部署配置，必须保持「调用时读 env」语义；2 个 import 期路径变量（ORDERS_DIR/STATE_DIR）保持冻结（test_execution 依赖 import 前设 env） |
| 8 | pipeline 测试全部先做还是全部后做？ | **折中**：P0 行为级场景先行，全套场景在 repo 稳定后补 | 全部先做会被 S2/S3 重构打散重写；全部后做意味着大重构裸奔。P0 场景全走公开 API（`runner.confirm(now=)` 等），不耦合实现细节 |
| 9 | 语法约束 | **Python 3.9** | 所有新代码禁止 `X \| Y` 联合类型语法等 3.10+ 特性（可用 `from __future__ import annotations` + `Optional[X]`） |
| 10 | 工程纪律 | 每个 Phase 独立 feature branch + squash merge，测试不绿不进下一阶段 | 任何 Phase 失败 revert 单个 commit 即可回滚 |

## 1. 事实基础（多 agent 摸底结论，2026-09-15/16）

设计与工作量估算基于以下已核实事实（行号为当时快照，实施时以实际为准）：

**配置层**
- config.json 加载点 16 处、四种策略并存：8 处 import 冻结（fetcher/news/blacklist/runner/paper/bundle/decide/review.daily）、5 处函数内每次重读（signals.py/movers.py/hot.py/regime.py/backtest.py）、1 处进程单例（notify）、1 处 mtime 缓存（webapp/server.py:91-106）。
- 硬索引（键缺失即 KeyError，崩点在业务深处）：`db_path`（fetcher.py:152）、`watchlist`（fetcher.py:621,638；news.py:181,272）、`blacklist_rules`（blacklist.py:16）、`risk` 段（engine demo）。→ schema 校验最小硬键集。
- webapp 是 ThreadingHTTPServer，mtime 缓存是唯一热更新点，语义：坏 JSON 保留旧缓存下次重试。

**口径函数**（5 处而非 3 处）
- `limit_pct`：engine.py:85（权威，含北交所）/ factors.py:100（生产死代码，仅测试引用）/ audit.py:37（百分数 +0.5pp **舍入容差**，非 ST 容差）/ paper.py 已改用 engine 版 / **backtest.py:121 内联第五处（缺北交所 30% 分支）**。
- `limit_price`：engine.py:112 与 paper.py:35 逐字符相同；调用点策略不同（engine 规则14「到板即拒 ≥」，paper「超板才拒 >」）——差异留在调用点，不进公共函数。
- 交易时段两套粒度**不可合并**：engine `in_trading_session` 秒级（11:30:01 ∉）、quotes `is_trading_time` 分钟级（11:30:30 ∈）。当前调用图下不造成成交分歧（buy/sell 必经规则4），但合并即行为变更。
- `data/trade_cal.py:5` 注释声称「风控时段判断统一引用本模块」与事实不符（engine 未引用），是过时注释。
- 循环导入安全：stdlib-only 的 `common/market.py` 放 BASE 根下，与所有潜在导入方无环（engine 模块级只有 stdlib，factors/quotes/audit 零项目 import）。

**裸 SQL**
- 实测约 300+ 处执行点/30+ 文件。最大重复簇：「最新交易日」13 处独立实现；「有效成交」过滤 3 份定义 8 个使用点（paper `_EFFECTIVE` / daily `_TRADE_OK` / runner 内联）；单票最新收盘 7 处；decision 行+JSON 解析 3 份；decision INSERT 2 份且列不一致（runner.py:274 vs decide.py:275）；trade INSERT 孪生（paper buy/sell）；`SELECT code FROM stock_info` 11 处。
- **webapp 从不跑 DDL**（server.py:117-122 自己的轻量 get_conn）——「webapp 每请求跑 15 条 SQL」是审查报告的错误说法；DDL 每连接重跑只发生在短命 pipeline 进程。
- 事务地雷 5 处（收敛红线，见 Phase 4）。
- `api_workflow`（server.py:637-757）对每条 trace 做 2 次子查询（risk_events + trade），30s 轮询下是主要 DB 开销 → N+1 消除收益点。

**pipeline**
- catchup 5 步（增量行情/缺日盯市+日报/盘前午评兜底+kill安全网/动态池/盘后当日补全）；`catch_up(now=)` 可注入；步骤1/3 是函数调用、其余子进程 `_run_script`（stub 它即可）；步骤2c 走裸 `subprocess.run`。
- 退出码约定：0=无可补/已齐、1=部分失败、2=触发 kill（仅 catchup↔intraday_check 之间成立；postclose 的 rc=2 不透传）。
- 测试陷阱：postclose L182 `date.today()` 不可注入（PENDING 分支只能在真实今天语义下测）；midday run_date 恒为真实今天（`--now` 只影响内容与产物目录）；catchup flock 要求测试避免并发。
- **DB 路径无任何 env 覆盖**（fetcher.py:28,152 硬读 config.json）→ 子进程黑盒测试目前无法隔离真实库。
- postclose 调 `data_audit.run(backup=True)` 会向真实 logs/backup 写 VACUUM 快照 → 测试需要 BACKUP_DIR 隔离。
- 通知静默：`AGSICKLE_DISABLE_NOTIFY=1` 调用时检查，随时设有效。

**前端**
- 轮询已收敛：全局 1 个 interval，30s 只拉 3 个轻接口（overview/workflow/pending），重页面纯手动刷新。
- ErrorBoundary **不存在**——渲染期异常即全站白屏，而 API 的 reasons/risk_notes 经 `parse_json_field` 动态解析，风险真实。
- `Cache-Control: no-store` 打在 `_send_bytes`（server.py:1014-1018）——**所有响应**的唯一出口，包括带 content-hash 的 `/assets/*`（vite 产物已默认 hash），每次刷新全量重拉 MB 级 bundle。
- 前端零测试（无 vitest/jest）；`npm run build` 含 `tsc --noEmit` 前置。

### Phase 3：common/config.py 统一配置层（1 天）

**设计**：stdlib（dataclasses + json），Python 3.9，零新依赖（ADR #1/#2）。

```python
# common/config.py
def load() -> dict      # mtime 缓存热读；坏 JSON 保留旧缓存下次重试（继承 webapp 语义）
def snapshot() -> dict  # 进程生命周期冻结快照（短命 pipeline 语义；返回普通 dict，可变——保测试注入）
def validate(cfg) -> list[str]  # 最小硬键：db_path / watchlist(list且元素含code) / blacklist_rules / risk
class ConfigError(Exception)    # 报错带精确路径：如 "risk.stop_loss_pct: expected float, got str"
```

- `snapshot()`/`load()` 首次调用跑 validate，硬键缺失/类型错 fail-fast——把现在「崩在 blacklist.py:16 业务深处」的 KeyError 提前到启动并给出可读信息。
- **迁移分 3 批**，每批独立 commit 可单独 revert：
  - 批1（低风险）：blacklist / regime / notify / ai.decide（顺带消除 decide.py import 冻结坏味道）
  - 批2（中）：fetcher / news / bundle / review.daily
  - 批3（高）：paper / runner / webapp.server（server 的 `load_config()` 改为转发 `config.load()`，保留 `CONFIG_PATH`/`_CONFIG_CACHE` 属性作为 test_webapp 注入 hook）
- 各模块 `CFG = json.loads(...)` 换成 `CFG = config.snapshot()`——**同名可变 dict**，`set_gate()` 原地 mutate、`START_CASH` 常量等测试手法全部继续可用。
- **容错分级保留**：notify 失败回退 {}、regime/signals 失败回退默认值，是刻意设计，不一刀切 fail-fast。
- AGSICKLE_* 不收编（ADR #7）。

验收：`grep -rn '(BASE / "config.json")' --include="*.py"` 只剩 common/config.py 一处；run_all 全绿；手工验证「改 config.json → webapp 不重启生效」与「短命 pipeline 进程读到新配置」两条路径；构造缺键 config 验证 ConfigError 报错可读。

### Phase 4：data/repo.py scoped 收敛 + N+1 消除（1-1.5 天）

**连接层统一**：
- 以 fetcher.get_conn 为基准，补 `row_factory = sqlite3.Row`（同时支持 `row[0]`/`row["name"]`，对现有 tuple 风格向后兼容）。
- DDL 从「每连接都跑」改为显式 `init_db()`（或 `get_conn(migrate=False)`，pipeline 入口各调一次 init_db）。
- `transaction()` 上下文管理器：**仅新代码使用**，旧代码不动。

**repo 函数清单**（返回值保持被替换处现状形状，ADR #3）：

| 优先 | 表 | 函数 | 收掉的重复 |
|---|---|---|---|
| 1 | trade | `TRADE_EFFECTIVE_SQL` 常量、`cash_flows(conn, as_of=None)`、`effective_trades_by_decision`、`trades_on(date, statuses)`、`insert_trade(...)` | 3 份 _EFFECTIVE 定义 8 用点；cash 4 口径参数化合一；paper buy/sell INSERT 孪生 |
| 2 | daily_bar | `latest_trade_date(conn)`、`latest_close(conn, code, offset=0)`、`latest_bars(conn, codes)`（批量版，供 N+1） | 13 处 + 7 处 |
| 3 | portfolio_state | `latest_state` / `state_on` / `has_state` / `peak_total(before, window)` | 5+3+3 处；peak 三口径参数化 |
| 4 | decision | `insert_decision`（runner/decide 两份对齐缺省列）、`get_decision_with_snapshot`、JSON 解析器三合一 | 列不一致问题一并解决 |
| 5 | stock_info | `all_codes(conn)`、`name_map(conn)`、`stock_names(conn, codes)`（批量版） | 11+ 处 |
| 附 | risk_event | 只读包装 2 个（kill 相关查询已收敛，不重写）；`record_event` 语义原样 | — |

**事务红线**（写进 repo 模块 docstring）：
1. repo 函数**一律不 commit**，事务控制权留给调用方；
2. `record_event` **保持自提交**（19 个调用点依赖「拒绝路径留痕后 raise」）；
3. paper.buy/sell 的「position+trade 单事务」原子性不得拆；
4. runner._execute 的「成交/状态两段提交」恢复语义不得合并；
5. decide.save 批量一 commit vs runner 逐条 commit 的粒度差异**保留现状**。

**不进 repo**：fetcher 的 DDL/_MIGRATIONS（迁移与表结构单一事实源，tests 直接 import DDL）、fetcher 采集型 upsert、webapp 一次性聚合展示查询（api_health/api_data_status/equity_curve）、signals/macro/trade_cal/universe800/news 领域写入（二期）、kill 查询主体。
