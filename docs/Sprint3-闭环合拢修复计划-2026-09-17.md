## §2 Fix-1：breadth_composite 真 z-score + 补齐 5 指标（1d）

**问题**（复审 TOP 5 #2，公式级 bug）：`data/breadth.py:203-240` composite 是原始值算数平均（量级几十），threshold=-2 永不触发 → regime 极端避险档死代码；`seal_rate` 硬编码 1.0；`new_high_minus_new_low` 恒 None。

### 改动
1. **`data/breadth.py` 新增 `_rolling_zscore(conn, col, window=250)`**：
   - 读 `breadth_daily` 近 window 日该列历史，返回 `(cur - mean) / std`；std=0 或样本 <60 → 返回 None
   - 冷启动：样本 60~249 → 用实际窗口并在结果 dict 标注 `z_window_actual`
2. **composite 公式改为加权 z**：
   ```
   composite = 0.30×z(limit_up_count) − 0.30×z(limit_down_count)
             + 0.20×z(advance_decline_ratio) + 0.20×z(new_high_minus_new_low)
   ```
   任一 z 为 None → 权重重归一化后加权；全部 None → composite=None
3. **`limit_up_seal_rate` 真实计算**：em 源加 `ak.stock_zt_pool_zbgc_em`（炸板池）→ 封板率 = 涨停数 / (涨停数 + 炸板数)；tx/sina 源保持 None（不硬编码 1.0）
4. **`new_high_minus_new_low` 从 daily_bar 全表扫**：60 日窗口内创 60 日新高的家数 − 创新低的家数（收盘价口径，qfq 优先）
5. 写库前把 `z_window_actual` 记入 `source` 字段（如 `em|z_window=87`）
6. **`signals/breadth.py` 不动**（threshold=-2 与真 z-score 量级匹配了）

### 测试（tests/test_breadth.py 新增 ≥4 case）
- z-score 正确性：合成 250 日历史 → 手算期望值比对
- 冷启动：<60 日 → composite=None；60~249 日 → 用实际窗口
- new_high_minus_new_low：构造已知新高/新低数据 → 计数正确
- seal_rate：mock 炸板池 → 封板率 = zt/(zt+zb)

## §5 Fix-4：规则 21 主动扫描 + confirm 优先超时兜底（1.5d，按 D1 决策）

**问题**（复审 TOP 5 #1，最严重）：规则 21 只在 LLM 主动提交跌停价卖单时被动响应；LLM 不主动卖时连续跌停死锁依然成立；无 stuck 计数与 kill 联动。

### 改动
1. **新表**（`data/fetcher.py` DDL + `_MIGRATIONS`）：
   ```sql
   CREATE TABLE IF NOT EXISTS limit_halt_stuck (
       code TEXT PRIMARY KEY, first_stuck_date TEXT,
       stuck_days INT DEFAULT 1, last_attempt TEXT
   );
   ```
2. **主动扫描器** `signals/limit_halt.py`（新文件）：
   ```python
   def scan_positions(conn, ctx_inputs) -> list[dict]:
       """对 position 表每只票判三条件（跌停价 / 封单比 / 浮亏≥stop_loss_line），
       复用 risk/engine.py::rule_limit_halt_emergency 同款判定逻辑（抽公共函数
       _limit_halt_condition(code, ctx, cfg) -> (bool, detail)，engine 与扫描器共用）。
       命中 → 生成 emergency sell decision dict（price=跌停价, shares=avail_shares）。"""
   ```
3. **接入 pipeline**：
   - `pipeline/postclose.py` 末尾：调扫描器 → 命中则走 `execution.runner.propose` 正常入库（decision 带 `"emergency_scan": True` 标记）→ `runner.confirm` 可用的 pending 落盘 → **macOS 通知**（osascript display notification，参考项目现有 notify 模式）
   - `pipeline/intraday_check.py` 14:50：同样扫描，已 stuck 的票更新 `limit_halt_stuck.stuck_days`（同票首日 insert、后续 +1）
   - `limit_halt_stuck` 达 5 日 → `record_event(rule='limit_halt_stuck')` + 通知人工；**同日 ≥3 只票 stuck → 触发规则 5 kill_switch**（调 `risk.engine.apply_kill_switch`，走既有人工 resume 链）
4. **超时兜底**（D1 核心，`pipeline/premarket.py` 步骤 0.5，在数据抓取之前）：
   - 查 decision 表昨日 `emergency_scan=True` 且 status 仍 approved（未 confirm 未 reject）的单：
     - 09:00：macOS 通知"有 N 笔跌停应急单待确认，09:14 将自动执行"
     - **09:14 检查仍未 confirm → 调 `runner.confirm(decision_id, confirmed_by="emergency_timeout_failsafe")` 自动执行**（confirm 内置风控复跑与 ±2% 价格校验，安全）
   - 时间窗判断用 `datetime.now()`，扫描器本身幂等（同票同日只生成一次，以 decision 表 code+action+date 去重）
5. **confirmed_by 审计链**：`emergency_scan`（扫描生成）→ `emergency_timeout_failsafe`（超时自动）/人工（confirm 时填真人名）→ trade 表可完整归因

### 测试（tests/test_risk_engine.py 或新建 tests/test_limit_halt.py，≥5 case）
- 扫描器三条件命中/不命中
- stuck 计数递增 + 5 日 risk_event
- 3 只 stuck → kill 触发
- 超时兜底：mock 时间 09:14+ 未 confirm → 自动 confirm 且 confirmed_by 正确
- 幂等：同票同日重复扫描不重复生成 decision
